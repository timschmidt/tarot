## Installed-app launching

The new [transient family policy](TRANSIENT_WINDOWS.md) has nested GLES protocol acceptance: mapped-parent ownership, modal hints, nested focus, late attach/detach, orphan/remap semantics and actual scale-1/2 input/pixels in every orientation. Protected mapping uses a trusted protocol-lock probe. Revisions 19–20 add real device touch/PAM, configure/remap history, four-orientation overflow pixels/input and GTK3/Qt6 long-menu selection beyond conservative dialog bounds. Revision 21 adds real root maximize/fullscreen/restore widgets and protocol negotiation/protection. Revision 22 adds real fullscreen bottom-field reservation, keyboard hide/reopen, overview/return and PAM restoration. Broader IME, wider constraints and arbitrary toolkit applications remain open.

The catalog applies XDG directory priority before visibility filtering, so a hidden user entry suppresses the corresponding system entry. Nested IDs remain stable. It retains localized metadata and reports missing executables or unsupported launch requirements. The first phone scan found 29 entries; the inspected host found 442. Counts depend on the installed applications and desktop visibility rules.

The metadata decoder is pinned `freedesktop-desktop-entry` 0.8.4 with gettext disabled. Tarot parses Exec into argv separately, expands name/path/icon and literal-percent fields, removes absent file/URI arguments, rejects unsupported or ambiguous codes, and passes arguments directly to `std::process::Command`. Shell syntax is literal unless the desktop entry explicitly selects a shell executable. `Terminal=true` entries use a typed foot command wrapper when available. D-Bus-only activation and live catalog refresh remain incomplete. [Desktop Exec specification](https://xdg.pages.freedesktop.org/xdg-specs/desktop-entry/latest/exec-variables.html), [decoder package](https://docs.rs/crate/freedesktop-desktop-entry/0.8.4/source/Cargo.toml)

The launcher has a searchable, virtualized three-column grid with preliminary letter icons. It deduplicates an application's pending startup and reports spawn/early-exit errors or a twenty-second window timeout. A later window clears pending feedback. pidfd readiness reaps child processes; a wait worker is the fallback when pidfd registration fails. No permanent process-polling timer is needed.

Cards and application focus are now created on the first committed root buffer, rather than the creation of an xdg-toplevel role. The real protocol regression in `tests/wayland_lifecycle.rs` passed in a nested session and directly on the PinePhone Pro. It verifies that an unbuffered second window cannot steal focus, a close request retains the card until the app cooperates, null-buffer unmapping removes it, remapping preserves its ID, and both explicit destruction and abrupt client disconnect remove stale cards. The post-change phone run again rendered GTK3, GTK4, Qt and foot together. This does not yet cover transient/dialog parenting or popup grabs.

Later popup tests are independent of that lifecycle coverage. The phone's unprivileged Rust probe exercises nested keyboard focus and touch targets, active-parent serial reuse after five seconds, parent restoration after child destruction, reverse-order dismissal through shell navigation, invalid-serial denial, fitted edge constraints and an intentionally late grab. The last case disconnects the invalid client while retaining other cards and the compositor. Calculator's GTK4 menu also passes real touch open/dismiss/reopen/overview checks. Pointer grabs, popup repositioning, Qt menus and transient dialogs still require dedicated coverage.

The ordinary eframe test exposed a callback starvation failure: its immediate secondary viewport shares a render thread with the hidden primary, so withholding the primary's callback blocked EGL swap and prevented the visible window from processing touch release. Callback eligibility now includes all windows sharing a visible Wayland connection; unrelated hidden clients progress at a four-Hz limit when they request frames. The real lifecycle fixture verifies both classes on desktop and phone. These callbacks permit drawing; they do not certify presentation of hidden content or sustained power/performance behavior.

Manual stack replay now groups GTK3 and an egui window while retaining the second egui window as another card. Real touches select either exposed member, reorder within the stack, extract/reorder a standalone card and flick only GTK closed while preserving its egui sibling's window and stack identity. Timed hold, edge paging, second-contact cancellation and the menu alternative are exercised. Shell menus now render above native content on a separate transparent layer. Automatic parent-based grouping, arbitrary transient dialogs and preserving group metadata across unmap/remap or a session restart remain outside this proof.

Development wrappers use `dbus-run-session` to keep single-instance applications in Tarot's session. On the host, first Calculator launch waited roughly thirty seconds for portal activation; the private session encountered portal/keyring/mount/accessibility-service conflicts with the parent desktop. The window eventually rendered correctly. These are interoperability issues to resolve; do not claim portal or accessibility support from this test, or change the host's global services to hide the problem.

## Native notification compatibility

The installed `notify-send`/libnotify 0.8.8-r0 client and an independent Rust D-Bus fixture run against the standard `org.freedesktop.Notifications` interface in Tarot's isolated phone session. No Tarot application SDK is required. The fixture verifies replacement IDs, revision-safe actions, directed signals, close reasons, explicit expiry, transient/resident behavior, critical retention, field/capacity limits and sender isolation. The real touch replay verifies banner/dashboard actions and settings, an arrival during card hold, typing with a banner above the native keyboard, and restoration of the same field after modal dismissal. A short-lived sender's entry stays visible with unavailable actions.

Advertised capabilities are `actions`, `body` and `persistence` (live retention until acknowledgement, not storage across restarts). Bodies are plain text; markup, icons/images, sounds, action icons, activation tokens and `inline-reply` are not advertised. An action named Reply is an ordinary action signal, not inline text entry. Owner checks use unique D-Bus connections within a connection epoch, so replacement across a client's reconnect is not supported. Nested regressions verify retention of an existing server, recovery after name release and bus replacement, stale-owner isolation, and usable settings/clean exit while offline. Old entries lose remote actions on bus replacement; local history remains in memory. DND/preview preferences persist through versioned atomic TOML saves with real phone restart evidence. Other toolkits' actual notification APIs, activation/focus integration, native bus-restart, durable history, packaging and authenticated lock redaction need further checks.

See [replay instructions](BUILDING.md#native-notifications) and the [implementation evidence](IMPLEMENTATION_STATUS.md#native-notification-service).

## Native network compatibility

The NetworkManager adapter uses standard system-bus methods, so native applications continue using the platform's existing network stack. A real UID-10000 phone session passed touch scan, saved-network activation, disconnect and software Wi-Fi radio off/on, while retaining USB and its GTK card. The exact original connection profile returned without administrative recovery. That initial checkpoint covered saved profiles; the subsequent new-network/secret-agent evidence appears below. Hidden-network setup and a Polkit agent remain unfinished.

The private D-Bus fixture additionally checks duplicate AP grouping, an open network sharing a protected network's name, nonsecret profile compatibility, stale identities, delayed confirmation, timeout, denied/auth-required actions, credential-needed state, hardware-unavailable feedback and service/bus recovery. These are protocol/adapter checks, not a physical RF-kill test, enterprise interoperability matrix, native service-outage test or completed Settings application. Captures can expose network names and remain ignored private evidence. [Replay instructions](BUILDING.md#wi-fi-controls), [implementation evidence](IMPLEMENTATION_STATUS.md#wi-fi-system-controls).

Visible open/personal setup and a restricted secret agent now extend that initial saved-profile checkpoint. Private-bus tests verify profile persistence options, private user permissions, password validation/redaction, foreign-caller/noninteractive rejection, cancellation and loss/shutdown with a populated prompt. The actual phone activated a new volatile profile and answered a real NetworkManager missing-password request for a memory-only QA profile. Both test profiles were removed, the original network and GTK card returned, and USB remained available. The existing credential was read only by root QA into memory and supplied through private control; a touch letter/delete and Enter submission were exercised. This is not complete touch transcription, enterprise/SAE interoperability, persistent personal-password reconnection across a native restart or general agent-owned secret storage. [Password evidence](IMPLEMENTATION_STATUS.md#connection-setup-and-secret-agent).

The subsequent persistence replay completes touch transcription of the personal password and reconnects a private disk-backed profile without entry in a different compositor process. Root QA verifies the new credential in memory only; NetworkManager remains running. The test profile/keyfile is removed and the original network restored. This adds compositor-restart evidence; daemon/reboot persistence, additional security modes and general agent-owned storage remain outside the proof. The shared keyboard also delivers all 95 printable ASCII characters by native touches. [Persistence and rendering evidence](IMPLEMENTATION_STATUS.md#remembered-profiles-printable-keyboard-and-resize-recovery).

A hidden shared-memory client resize regression now checks fresh pixels after grow/shrink while unmapped from view. It reproduced an out-of-bounds partial texture upload in pinned Smithay 0.7; the attributed upstream clipping backport passes on desktop Mesa and native Panfrost, as do the previously failing keyboard-to-launcher sequence and ordinary lifecycle/callback checks. The wrapper rejects GL errors even when the protocol test and compositor exit successfully.

## Native audio compatibility

Playback controls use the ordinary user's standard PulseAudio-compatible server rather than a Tarot application API. The phone's PulseAudio 17 internal-speaker volume/mute and default output pass native UI touches with independent `pactl` readback. Only a temporary null sink is used for the second-output/default test; it and the QA subscription client are removed, and exact channel values/mute/default restored. No acoustic playback or capture is claimed. A private real-PulseAudio daemon exercises balance, zero/same-value completion, external changes, hotplug, delay/timeout, daemon replacement and exit while pending. PipeWire runtime, physical devices/profiles/ports, microphones, per-app routing and call audio remain separate checks.

New native windows no longer dismiss an open system/notification panel or replace the panel's underlying selection. First-map preservation has a failing pre-fix Wayland regression and passing corrected desktop/native runs. Explicit egui panel/scrim ordering also preserves interactive controls after outside dismissal and reopening; the final audio → power → notification native sequence passes. These focus/layering changes do not certify transient-parent, activation-token, authenticated lock or general accessibility policy. [Audio and modal evidence](IMPLEMENTATION_STATUS.md#playback-audio-and-modal-recovery), [reproduction](BUILDING.md#audio-controls).

## DMA-BUF evidence

The first successful four-client phone run recorded seven renderer-validated DMA-BUF imports and zero rejections. GTK4 Calculator's process exposed Panfrost DRM client IDs 170 and 172 with resident allocations; repeated descriptors for the same ID must be deduplicated. Screenshots of GTK4 Calculator, Qt/Kalk and foot were inspected. Native-client GPU support is now more than protocol advertisement, but format/modifier coverage, malformed-client isolation, explicit synchronization and presentation timing still require tests.

The session publishes the active renderer's import formats. Where EGL identifies a DRM device, clients receive version-4 device feedback; otherwise version 3 is available when import formats exist. Every creation request is checked with the actual renderer. Failed imports notify the client and increment diagnostic counters. [Pinned Smithay DMA-BUF implementation](https://docs.rs/smithay/0.7.0/smithay/wayland/dmabuf/index.html)

## Experimental session protection

The opt-in synthetic locker has nested and native protocol evidence; it is not an authenticated user lock screen. While protected, normal clients receive no fresh keyboard/touch input, ordinary shell commands/captures and card metadata are denied, cached clipboard receive requests are blocked, and normal app rendering/frame callbacks are withheld. Existing clipboard content and app focus return after a valid owning unlock. New app mapping/unmapping and normal keyboard-helper replacement preserve an active locker touch. Owner death, rejected second-lock unlock and destroyed lock-surface role retain opaque protection; trusted replacement recovers without exposing the scene. The direct test also covers VT release/reacquisition.

This does not sandbox native Linux processes or revoke previously transferred clipboard bytes. Physical mouse-held variants, arbitrary toolkit grabs, rotation, multi-output, sustained suspend and authenticated startup remain unverified. [Evidence and exact scope](IMPLEMENTATION_STATUS.md#session-lock-protocol-foundation)

## Authenticated client follow-up

The actual `tarot-lock` egui/EGL client now requests the real lock role through the trusted connection, uses a private embedded keyboard instead of the normal input method, and verifies the current UID through Linux-PAM. Native tests cover an incorrect physical-keyboard entry, correct touch entry followed by Cancel, then complete touch re-entry and authenticated unlock. Normal GTK/chrome captures return afterward. A separate normal-session replay verifies notification/modal/power and native-field typing after extraction of the shared EGL renderer. This does not establish automatic locking, repeated user Lock actions, startup privacy, suspend/resume, all password layouts or application process sandboxing. [Evidence](IMPLEMENTATION_STATUS.md#authenticated-rustegui-locker)

## Repeated-lock and startup policy

With a locker configured, ordinary application mapping can occur behind startup protection without taking foreground focus or exposing app metadata. Native evidence now covers a protected first KMS frame, automatic real-locker recovery and a second user-triggered lock/authentication preserving card IDs, view and closed-panel state. Host protocol evidence additionally covers stale timers, destroyed roles, missing executables, startup hangs, missing first UI buffers and bounded retry exhaustion. Diagnostic protocol fixtures use the explicit unlocked-start option; normal sessions retain the protected default. Suspend, packaged greeter restart, exhausted-recovery UI and broader application/input cases remain separate gates.


## Surface idle inhibition

`zwp_idle_inhibit_manager_v1` is now available to ordinary Wayland clients. Actual protocol tests cover two objects for one surface, explicit release, hidden/restored windows, an opaque child fully covering its parent, unmapping and abrupt client death. Inhibition requires a mapped surface with nonzero renderer-visible area on the active output. A late inhibitor cannot wake an already idled panel or override explicit locking/sleep preparation. Resource handles are retired even with automatic idle disabled. Objects/counts are not exposed in protected diagnostics. Native evidence and limits are recorded in the [idle/panel checkpoint](IMPLEMENTATION_STATUS.md#idle-locking-and-panel-power).

This is surface-scoped idle inhibition, not general media/background scheduling. `ext-idle-notify`, D-Bus ScreenSaver/portal inhibition, audio/call inhibitors, proximity and automatic suspend policy remain separate work. Renderer visibility uses declared opaque regions; arbitrary translucent overlays and all toolkit-specific media behaviors still need broader coverage.
