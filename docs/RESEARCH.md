# Tarot technical research

Research began October 26, 2026, with implementation findings added October 27. Architecture choices derived from these findings are proposals until the corresponding experiments pass. Hardware behavior must be measured on the actual development phone.

## Project and platform baseline

At the initial inspection, the repository contained a Rust 2024 binary package named `tarot`, version `0.1.0`, an empty dependency list, and a main function that printed `Hello, world!`. No existing implementation constrained the design. Implementation has since produced the workspace described in [current status](IMPLEMENTATION_STATUS.md). The inspected development environment has Rust and Cargo 1.98.1; the workspace minimum is now 1.89. An actual Rust 1.88 check rejects locked `uuid` 1.29.0 (through zbus 5.16.0); an isolated Rust 1.89 host workspace test passes all 104 ordinary tests. The same minimum compiler also passes the complete AArch64/musl DRM workspace/all-target check; target tests were not executed by that check. The Alpine source package uses the recorded Rust 1.96.1 distribution compiler.

The owner confirmed that Tarot should be a complete phone shell supporting native Linux applications, that standard Linux dependencies are compatible with the Rust requirement, and that WebOS's visual and behavioral design should remain recognizable on modern foundations. A spare PinePhone Pro is available, with development control and an OS update authorized. Its initially unknown installation was identified as 24.12 and upgraded through supported releases to stable 26.06, kernel 7.0.0 and Mesa 26.1.6. [Observed device baseline](DEVICE_BASELINE.md)

Nura is the current name of the distribution formerly called postmarketOS; upstream announced the change on September 27, 2026. Some domains and package names retain the old name. Use Nura in Tarot prose while preserving actual upstream identifiers. [Nura announcement](https://nura.eco/blog/2026/09/27/nura-rename/)

The current installation page lists v26.06 as the latest stable release and offers stable and edge images for the PinePhone Pro. This is a dated observation, not a permanent version requirement: resolve the latest supported release again when provisioning. [Nura installation page](https://nura.eco/install/)

Two distribution changes affect the development plan:

- An August 30, 2026 edge notice describes the PinePhone Pro transition to distribution-managed U-Boot and systemd-boot, including an incompatibility with the older Tow-Boot chain. This is an **edge update notice**; it must not be applied indiscriminately to stable installations. Identify the selected image and existing boot chain before following its matching instructions. [PinePhone Pro boot transition](https://nura.eco/edge/2026/08/30/pinephonepro-u-boot/)
- A July 10, 2026 notice describes UI packages declaring supported service managers. Tarot should explicitly support and test one initial service-manager configuration, then expand if useful. Neither “Nura always means OpenRC” nor “every UI works under both managers” is a sound assumption. [UI service-manager support](https://nura.eco/edge/2026/07/10/explicit-service-managers/)

The device wiki redirected to an access challenge during this research. An older search index exposed historical feature statuses, but those are not a current hardware certification. Battery, calls, SMS, camera, USB, and suspend status remain device-test items; no historical kernel version or support table is adopted as the baseline. [PinePhone Pro device wiki](https://wiki.nura.eco/wiki/PINE64_PinePhone_Pro_%28pine64-pinephonepro%29)

## Hardware and rendering

PINE64 specifies a Rockchip RK3399S, Mali-T860 GPU, 4 GB RAM, 128 GB eMMC, a 720 by 1440 display, and a Quectel EG25-G modem for the PinePhone Pro. The target architecture is AArch64. The display's physical resolution must be distinguished from the shell's logical coordinate system. [PINE64 device specifications](https://pine64.org/devices/pinephone_pro/)

Mesa's Panfrost table lists the T860 as Midgard with OpenGL ES 3.1 and OpenGL 3.1 support, with no Vulkan entry. PanVK targets Bifrost and newer architectures. **Inference for Tarot:** use EGL/OpenGL ES as the initial hardware path; a Vulkan-only renderer would be an unsuitable baseline. This does not rule out every wgpu backend, but a GLES-based wgpu path would still need its own interoperability and performance validation. [Mesa Panfrost documentation](https://docs.mesa3d.org/drivers/panfrost.html)

Smithay supplies Wayland compositor building blocks and backend abstractions; it does not supply Tarot's window-management policy. Its documentation describes a calloop-driven event loop, and its Anvil example demonstrates nested and direct device backends. [Smithay architecture](https://smithay.github.io/smithay/smithay/), [Anvil backend examples](https://github.com/Smithay/smithay/blob/master/anvil/README.md)

Smithay also documents a `GlowRenderer` over its GLES renderer. This makes an egui/OpenGL integration a credible starting point, but does not prove that a particular pair of crate versions can share contexts or rendering state correctly. [Smithay glow integration](https://smithay.github.io/smithay/smithay/backend/renderer/glow/index.html)

egui accepts input and produces shapes, texture updates, and platform output. Its host is responsible for rendering and integration. `egui_glow` is an available OpenGL painter; its documentation explicitly describes GL state changes that an embedding renderer must accommodate. **Inference for Tarot:** render shell chrome with egui while retaining client surface composition in Smithay, and validate the boundary before building extensive UI. [egui integration](https://docs.rs/egui/latest/egui/#integrating-with-egui), [egui_glow painter](https://docs.rs/egui_glow/latest/egui_glow/painter/struct.Painter.html)

## Dependency and test candidates

At inspection, egui documentation identifies version 0.37.0 and a Rust 1.95 minimum. Smithay's latest published GitHub release is v0.7.0; its release manifest uses glow 0.16 and contains explicit rendering/backend feature flags. Development-branch examples can differ from a published release despite similar version labels. Resolve compatible versions in the first experiment, pin them, and use matching documentation. [egui crate documentation](https://docs.rs/egui/latest/egui/), [Smithay release](https://github.com/Smithay/smithay/releases/tag/v0.7.0), [Smithay release manifest](https://github.com/Smithay/smithay/blob/v0.7.0/Cargo.toml)

`egui_kittest` supports semantic interaction tests through AccessKit. Its image snapshot path uses wgpu, so those snapshots alone cannot validate Tarot's proposed GLES rendering path. Pair semantic tests with captures from the actual compositor renderer. [egui_kittest](https://github.com/emilk/egui/tree/main/crates/egui_kittest)

Other candidates, to evaluate rather than add wholesale, are serde/TOML for configuration, tracing for diagnostics, a bounded asynchronous runtime for service work, and Rust bindings to platform libraries where necessary. Database selection can wait until durable application data is implemented.

## Ordinary egui client findings

October 27, 2026 implementation findings from pinned source and real phone tests:

- An ordinary eframe 0.33.3/Glow/Wayland app runs on Panfrost as independent xdg-shell cards. Its immediate secondary viewport can render through the primary's event/render thread. Withholding callbacks from that hidden primary stalls EGL swap and visible input. Tarot now prioritizes windows by visible Wayland connection and throttles other hidden requesters. Smithay's surface-tree helpers include subsurfaces/popups and expose the committed callback lists used to avoid permanent background timers. [Pinned Smithay frame helpers](https://docs.rs/crate/smithay/0.7.0/source/src/desktop/wayland/utils.rs), [pinned eframe integration](https://docs.rs/crate/eframe/0.33.3/source/src/native/glow_integration.rs)
- Pinned egui-winit 0.33.3 forwards a bare native IME commit without beginning a new composition; TextEdit can then discard a later commit because its saved composition cursor is stale. Tarot's reusable client host adapter begins bare compositions, preserves real preedit/cursor guards and keeps state per viewport. Trying to work around this with two keyboard transactions broke serial validation when the client replied with updated surrounding context; atomic protocol commits were retained. [Pinned egui-winit event handling](https://docs.rs/crate/egui-winit/0.33.3/source/src/lib.rs), [pinned TextEdit handling](https://docs.rs/crate/egui/0.33.3/source/src/widgets/text_edit/builder.rs)
- Winit 0.30.13 does not supply surrounding text or handle deletion requests in its Wayland text-input implementation. Its IME purpose does map to native content type. The phone fixture verifies Tarot's virtual Backspace fallback and explicitly requested password purpose, including the private keyboard label and masked field. This does not cover every purpose/toolkit or certify secure locking. [Pinned winit text input](https://docs.rs/crate/winit/0.30.13/source/src/platform_impl/linux/wayland/seat/text_input/mod.rs)

See [implementation status](IMPLEMENTATION_STATUS.md) for exact build hashes, retained evidence and limits.

## Notification implementation findings

The October 27 implementation uses the standard notification interface, without an application SDK. The protocol defines replacement IDs, capabilities, actions and distinct close reasons; banner visibility is Tarot presentation policy, separate from the remote notification's lifetime. `persistence` describes retaining a live entry until acknowledgement and does not promise on-disk history. Tarot currently advertises only actions, plain body text and persistence. [Notification protocol](https://specifications.freedesktop.org/notification/latest/protocol.html), [basic design and capabilities](https://specifications.freedesktop.org/notification/latest/basic-design.html)

Typed urgency, resident and transient hints affect the store; unknown hints are ignored and image/sound features are not advertised. Critical entries do not auto-expire. The ordinary default is a five-second banner with live dashboard retention; explicit expiration and transient closure are separate. This is an initial policy rather than a completed urgency/phone-interruption design. [Hints](https://specifications.freedesktop.org/notification/latest/hints.html), [urgency levels](https://specifications.freedesktop.org/notification/latest/urgency-levels.html)

The installed libnotify client and two independent D-Bus fixture senders provide real phone evidence for interoperability, lifetime and signal routing. Nested tests cover an existing name owner and loss of the private session bus. Unique sender names constrain mutation and action delivery; app names/icons are presentation metadata. Sender disconnect disables actions while preserving content, which is necessary for short-lived clients such as `notify-send`. Durable history, authenticated lock privacy and application activation remain open. See the [compatibility record](APPLICATION_COMPATIBILITY.md#native-notification-compatibility).

## Settings and recovery findings

The XDG specification requires absolute base paths, defines the configuration-home fallback, and specifies private creation of missing configuration directories without changing existing directory permissions. Tarot now uses a versioned TOML file at that location, with atomic replacement and worker-thread file/directory sync. Real filesystem tests cover preservation of invalid/newer files, symlinks, bounded size, permissions and write-failure retry. The phone touch test saves both notification preferences, verifies them before input in a second compositor session, and saves defaults again. [XDG base-directory specification](https://specifications.freedesktop.org/basedir/0.8/)

Pinned zbus 5.16.0 supplies explicit name flags, blocking connections and method timeouts. The adapter reconnects using the supplied address, with bounded backoff; a fixed GUID remains an identity constraint, so a replacement daemon must actually be reachable at a valid configured address. On a new bus, unique names can be reused. Tarot therefore retires old actions/signals/deadlines and keeps IDs increasing across attempts, rather than treating matching sender strings as continuity. Nested restart and collision-release replays verify recovery and directed actions after reconnection. [Pinned connection API](https://docs.rs/zbus/5.16.0/zbus/blocking/connection/struct.Connection.html), [pinned builder source](https://docs.rs/crate/zbus/5.16.0/source/src/connection/builder.rs)

Initial startup also needed attention: synchronous activation-environment publication could otherwise exit before the retry worker started. Notification-enabled sessions now publish that environment through the worker on each connection. Real initial-offline and runtime-outage tests distinguish starting without a bus from losing one after startup. Native phone bus-restart, broader service recovery, startup application coordination, durable history and general settings beyond notification preferences remain to be verified or implemented.

## Power and display findings

The phone's UPower 1.91.0 exposes a composite display device and standard property-change signals. Its observed state was discharging at 43–44% while external power was connected. Tarot keeps charge state and supply presence separate, validates percentages, and prefers a supplied coarse level. The real device test compares a fresh UPower percentage to the shell snapshot. [UPower service](https://upower.freedesktop.org/docs/UPower/), [device properties](https://upower.freedesktop.org/docs/Device.html)

The panel backlight has maximum 51 and initially requested/actual level 15. Elogind 255.24-r0 implements the standard session brightness method. A request from the SSH session was rejected because it had no seat. A temporary local UID-10000 session on VT8 then allowed the unprivileged compositor to change levels by touch, with actual sysfs readback. No permission or Polkit rules were relaxed. [Session brightness API](https://www.freedesktop.org/software/systemd/man/254/org.freedesktop.login1.html), [installed-version session implementation](https://github.com/elogind/elogind/blob/v255.24/src/login/logind-session-dbus.c)

The bounded fixture initially inherited the SSH cgroup and was rejected with SessionBusy. Its corrected launcher detaches only its own new gated child before `CreateSession`, leaving existing sessions untouched. Elogind may remove that session as its leader exits, so release handles an already-removed session; privileged experiment cleanup can restore only the pre-launch brightness if the session has already gone. The harness records helper, compositor and VT-launcher status independently. This is development-session evidence, not authenticated greeter packaging or lock certification. [Installed-version session creation](https://github.com/elogind/elogind/blob/v255.24/src/login/logind-dbus.c)

Isolated D-Bus fixtures test initial bus absence, property updates, coarse/invalid levels, denied and delayed requests, readback mismatch, inactive/remote sessions, service loss/reacquisition, bus restart and invalid driver range. Native bus outages, hotplug/multiple-output policy, suspend, battery safety/critical-action policy and brightness persistence remain open.

## NetworkManager implementation findings

The October 27 implementation uses `RequestScan` with `LastScan` property-change confirmation. A successful method return acknowledges the request; it does not establish completed scan results. Saved activation uses an explicit profile, Wi-Fi device and compatible AP; completion follows the returned active connection and observed connected state. `WirelessEnabled` is distinct from the global networking switch. The radio test retained USB throughout. [Wireless device API](https://networkmanager.pages.freedesktop.org/NetworkManager/NetworkManager/gdbus-org.freedesktop.NetworkManager.Device.Wireless.html), [manager API](https://networkmanager.pages.freedesktop.org/NetworkManager/NetworkManager/gdbus-org.freedesktop.NetworkManager.html)

Raw SSID bytes and security determine grouping/profile compatibility, while presentation labels are escaped separately. The adapter reads nonsecret saved settings through `GetSettings` and never requests `GetSecrets`. Its initial saved-profile security matching accepts compatible open, PSK/SAE and existing enterprise profiles. New visible open/personal network setup and a restricted secret agent were added next; enterprise configuration and all security modes are not implemented. The private fixture exercises an open network with the same display name as a protected network and rejects incompatible activation. Native evidence covers the phone's existing personal-security profile only. [Saved connection API](https://networkmanager.pages.freedesktop.org/NetworkManager/NetworkManager/gdbus-org.freedesktop.NetworkManager.Settings.Connection.html), [Wi-Fi security settings](https://networkmanager.pages.freedesktop.org/NetworkManager/NetworkManager/settings-802-11-wireless-security.html)

The phone initially returned auth/no permissions despite libelogind reporting Tarot's temporary session as local, active and on seat0. A direct authorization check exposed a ConsoleKit database error. The running authority was an old deleted executable; the installed polkit-elogind 127-r2 executable linked libelogind. Starting the installed authority restored allowed Wi-Fi permissions without changing authorization rules. This demonstrates why package identity, running executable and session identity must be inspected separately. The upstream systemd/elogind backend uses session/seat and UID activity information. [Polkit 127 session monitor](https://github.com/polkit-org/polkit/blob/127/src/polkitbackend/polkitbackendsessionmonitor-systemd.c)

The real phone touch replay passed scan completion, saved activation, disconnect and software radio off/on, exact original-profile restoration and USB preservation. Private-bus tests cover delayed replies/state confirmation, timeout, denial, credential-needed state and service/bus replacement. Normal greeter/PAM packaging, Polkit authorization, persistent agent-owned secret storage, physical hardware switches, hidden networks and native system-service outage tests remain separate work.

`AddAndActivateConnection2` distinguishes disk and volatile profile persistence; volatile profiles are removed on disconnection. Tarot creates a private user profile and leaves storage to NetworkManager. The first native temporary-profile attempt combined volatile persistence with NOT_SAVED secrets and was immediately asked for a password again. Keeping the supplied secret system-owned within the volatile profile allowed activation without writing a persistent profile. This runtime observation is recorded separately from the private fixture's persistence-option assertions. [Creation and persistence options](https://networkmanager.pages.freedesktop.org/NetworkManager/NetworkManager/gdbus-org.freedesktop.NetworkManager.html), [Wi-Fi secret flags](https://networkmanager.pages.freedesktop.org/NetworkManager/NetworkManager/settings-802-11-wireless-security.html)

NetworkManager's secret-agent API is a reverse request to a registered user's agent. Tarot implements it on the standard object path, restricts prompts to an explicitly requested personal connection and checks the live unique daemon owner before and after input. It does not request stored secrets from a saved profile. Pending replies use a bounded asynchronous channel, with distinct user/daemon cancellation and no general agent-owned password store. Unsupported/noninteractive/foreign-profile requests return an error without prompting. [Secret-agent interface](https://networkmanager.pages.freedesktop.org/NetworkManager/NetworkManager/gdbus-org.freedesktop.NetworkManager.SecretAgent.html), [agent registration](https://networkmanager.pages.freedesktop.org/NetworkManager/NetworkManager/gdbus-org.freedesktop.NetworkManager.AgentManager.html)

The owned entry buffer uses pinned zeroize 1.8.2, redacted Debug and a fixed input bound. The masked widget renders bullets without TextEdit undo/history storage; physical private entry bypasses ordinary text routing. These measures do not establish that every copy in input libraries, D-Bus marshalling, the OS or a QA process is scrubbed. [Pinned zeroize guarantees and limits](https://docs.rs/zeroize/1.8.2/zeroize/)

## Persistence and SHM resize findings

A native remembered-profile test checked a persistent filename and Unsaved=false, then compared the credential in the new root-owned mode-0600 keyfile in root QA memory only. A new compositor process later activated the profile without entry. NetworkManager itself was not restarted. GetSettings excludes secrets, and an omitted autoconnect setting has default true; the initial QA verifier incorrectly required the explicit setting. Tarot continues leaving saved credentials to NetworkManager. [Saved connection properties](https://networkmanager.pages.freedesktop.org/NetworkManager/NetworkManager/gdbus-org.freedesktop.NetworkManager.Settings.Connection.html), [connection defaults](https://networkmanager.pages.freedesktop.org/NetworkManager/NetworkManager/settings-connection.html)

A keyboard/launcher transition exposed an out-of-bounds partial SHM upload in Smithay 0.7, reproduced independently by hidden buffer growth/shrink. Upstream commit e76b1eece59f0ccf87a04f7eaa6762e4f6e8dfee intersects accumulated damage with the current buffer. Tarot backports exactly that change into the published release source with full upstream notices. Tests now inspect fresh pixels and reject GL errors because a successful capture/process exit alone missed the latched error on the original desktop reproduction. Both desktop Mesa and native Panfrost pass after the fix. [Upstream fix](https://github.com/Smithay/smithay/commit/e76b1eece59f0ccf87a04f7eaa6762e4f6e8dfee), [local provenance](../third-party/README.md#smithay-gles-damage-backport)

## Playback audio findings

The inspected user audio endpoint is PulseAudio 17.0, with the PinePhonePro RT5640 ALSA/UCM card in HiFi (Mic, Speaker), a stereo internal-speaker sink and an internal-microphone source. PipeWire tools are installed, but that alone does not identify the active sound server. The observed speaker volume was 57672 on both channels (about 88%), unmuted. Voice-call, earpiece and headphone profiles exist; they have not been functionally certified.

PulseAudio's asynchronous introspection API supplies sink/server queries, volume/mute/default control and subscriptions. All access associated with a threaded mainloop must hold its lock; stopping the loop must release it. Tarot uses the low-level Rust bindings with a narrow explicit request/callback owner, leaving drivers and policy in the system stack. Acknowledgement is followed by observed state confirmation. The private real-daemon replay checks volume balance, delayed replies, timeout, loss/restart and pending shutdown. [Server control](https://www.freedesktop.org/software/pulseaudio/doxygen/introspect.html), [subscriptions](https://www.freedesktop.org/software/pulseaudio/doxygen/subscribe.html), [threaded mainloop](https://www.freedesktop.org/software/pulseaudio/doxygen/threaded_mainloop.html), [pinned bindings](https://docs.rs/libpulse-sys/1.23.0/libpulse_sys/)

PipeWire describes pipewire-pulse as its PulseAudio-compatible service. This supports choosing one standard control API for the current phone and future PipeWire sessions; it does not prove every routing/profile behavior is identical. Tarot labels default selection as applying to new playback, preserving existing app routing until a deliberate broader routing policy is implemented. [PipeWire PulseAudio service](https://docs.pipewire.org/page_man_pipewire-pulse_1.html)

## Modal startup and layer-order findings

Native audio testing opened the status menu before GTK committed its first buffer. Unconditional new-window activation then closed the menu; a reduced Wayland regression reproduces that ordering and passes after new cards retain modal ownership and the underlying selection. Another native sequence dismissed Audio via its scrim and reopened Power. egui automatically promotes clicked Areas, leaving the shared foreground scrim above the controls. The corresponding pointer test fails before explicit panel/scrim sublayer ordering and passes afterward for system and notification panels. [Pinned egui sublayer contract](https://docs.rs/egui/0.33.3/egui/struct.Context.html#method.set_sublayer)

A successful same-value volume operation exposed a separate event-coalescing mistake: unchanged service values do not imply that a pending UI request has already been retired. Audio completion now forces a result publication even when the observed volume is unchanged. Both private-server and native zero-volume boundary checks pass. These are observed Tarot fixes, not claims that the upstream sound server failed.

## Questions that experiments must answer

1. Which pinned Smithay, egui, and glow versions share a usable rendering integration on desktop and Mali-T860?
2. Can shell overlays, transformed client surfaces, clipping, and buffer reuse remain correct without full-screen CPU copies?
3. Which Nura release, kernel, Mesa, boot configuration, and service manager provide the best reproducible device baseline?
4. How do GTK, Qt, browser, and egui clients behave under the selected text-input, scaling, popup, and activation protocols?
5. What are the phone's actual frame time, idle CPU, power draw, touch latency, suspend reliability, and telephony limitations?
6. Which original WebOS details survive observation as essential, and which need explicit adaptations for Linux clients and an on-screen gesture region?

The [development plan](DEVELOPMENT_PLAN.md) assigns these questions to milestones and defines the evidence needed to close them.

## Session-lock protocol and pinned Smithay findings

Inspected October 27, 2026. `ext-session-lock-v1` separates compositor protection from trusted-client authentication. Acceptance alone is insufficient: the acknowledgement follows presentation of protected content on every output; normal content/input must remain hidden, and owner death must not unlock. Destroying a lock-surface role requires solid fallback even if its `wl_surface` remains alive. The compositor may restrict the interface to a launched client and permit a trusted replacement owner. Tarot implements this for its one selected output; native tests observe KMS completion while nested tests only observe EGL submission. [Protocol source](https://github.com/wayland-mirror/wayland-protocols/blob/main/staging/ext-session-lock/ext-session-lock-v1.xml)

Pinned Smithay 0.7 posts `InvalidUnlock` when a lock object has not received acknowledgement but falls through to its unlock handler. A local early return is necessary for this implementation. A deliberately unguarded build failed the same real-client replay: a rejected second lock object unlocked the active session and exposed ordinary card metadata. Guarded nested and native runs remain protected and recover through a new trusted connection. This is evidence about the pinned integration, not a claim about all current upstream versions. The inspected upstream revision uses an owning-lock/state check instead: [immutable `lock.rs` at 6b37edc](https://github.com/Smithay/smithay/blob/6b37edc019889148608a73e3e27423979cd642c8/src/wayland/session_lock/lock.rs).

A clipboard offer issued while unlocked can still be retained and used later. Clearing focus alone did not constitute the required policy boundary. The local default-allow selection hook rejects new receive/selection/drag requests while protected, including cached offers, while preserving the original source for unlock. It cannot revoke completed or previously authorized transfers. A role-liveness check and removal of dead output resources complete the current local session adaptation. [Patch and attribution](../third-party/README.md#smithay-session-protection-changes)

Wayland-client 0.31.15 consumes `WAYLAND_SOCKET`, removes it from the environment and marks the adopted descriptor close-on-exec. Tarot passes only the explicit child's socket descriptor across exec; ordinary clients connect to the public display without lock permission. Capability revocation and an event-loop wake track connection loss. Same-UID process/filesystem access is outside this protocol boundary. [Pinned connection implementation](https://docs.rs/crate/wayland-client/0.31.15/source/src/conn.rs)

The synthetic client intentionally has no authentication and supplies no evidence for PAM, login throttling, credential zeroization, lock-screen fidelity or idle/suspend startup ordering. ## Same-user PAM authentication findings

The verified phone has Linux-PAM 1.7.1-r2, `libpam.so.0`, and a root:shadow setgid `unix_chkpwd`. Distribution defaults live in `/usr/lib/pam.d`: `base-auth` includes pam_unix, nologin and environment policy, while `base-account` checks account validity. The existing `/etc/pam.d/vlock` refers to `system-auth`, which was not present in the inspected include directories; Tarot uses its own explicit base-auth/base-account service instead. No shadow/password database was copied or modified for this implementation.

Linux-PAM separates authentication and account management; checking only the password would miss account restrictions. The new narrow Rust boundary uses its public application/conversation ABI, invokes both checks and ends the handle. A private real-PAM permit/deny test confirms that either authentication or account rejection prevents acceptance. The host sandbox denies the audit netlink socket, causing PAM system error 4; run this explicit integration test outside that sandbox. Ordinary tests do not require PAM runtime modules. [Application API](https://github.com/linux-pam/linux-pam/blob/master/libpam/include/security/pam_appl.h), [conversation ABI](https://github.com/linux-pam/linux-pam/blob/master/libpam/include/security/_pam_types.h)

PAM's Unix helper is designed to validate the caller's own account without making the graphical client privileged. Actual phone tests confirm the standard configured path from an ordinary UID-10000 Tarot worker, with wrong rejection and real-password acceptance. Tarot does not invoke `unix_chkpwd` directly or read `/etc/shadow`. [Helper implementation](https://github.com/linux-pam/linux-pam/blob/master/modules/pam_unix/unix_chkpwd.c)

Authentication runs in a disposable child because third-party PAM modules may block or change process state/environment. A parent-owned timeout/process group and a parent-death signal limit the current worker lifecycle; production service supervision remains pending. Native GL captures cover only the trusted lock client's own clock/keyboard/bullets, explicitly enabled for QA. Normal compositor captures remain denied. These observations establish an initial authenticated client, not completed lock startup, automatic recovery, idle/suspend or production packaging.

## Actual kernel sleep measurement and resume re-arm

Follow-up, October 27: kernel capability inventory and a successful signal helper are insufficient sleep evidence. `CLOCK_MONOTONIC` pauses during suspend; `CLOCK_BOOTTIME` continues. The native probes therefore measure suspended time as boottime elapsed minus monotonic elapsed, alongside kernel success/failure counters and logged entry/exit. The independent pre-sleep observer also uses a boottime deadline, so a sample obtained only after wake cannot pass its two-second proof. Wall-clock log timestamps alone are not a duration measurement. [Kernel clock semantics](https://docs.kernel.org/core-api/timekeeping.html)

Linux distinguishes s2idle from deep suspend, including their wake sources and platform requirements. RTC alarm capability is device-specific, so the QA first verifies UTC mapping, wake enablement and an awake alarm on the actual rk808 RTC. Then it programs an owned alarm and requests normal elogind Suspend, preserving any pre-existing alarm. On this baseline the normal manager selects deep: stock sleep lasts 14.33 seconds and the first Tarot cycle 14.21 seconds. Those observations do not certify s2idle, a physical power key, carrier wake or every hardware path. [Sleep states](https://docs.kernel.org/admin-guide/pm/sleep-states.html), [RTC interfaces and hardware limits](https://docs.kernel.org/admin-guide/rtc.html), [measured evidence](IMPLEMENTATION_STATUS.md#actual-kernel-suspend-and-rtc-wake)

Repeated native cycles exposed a fixture mismatch: real elogind rejects delay inhibitors while its delayed action is still running, sometimes briefly after the false resume signal. The former fixture always granted them. Tarot now retries only `org.freedesktop.login1.OperationInProgress` within the same connection for a bounded three seconds, prevents unlock while re-arming, and reconnects protected on other/continued failures. The updated fixture rejects requests during preparation and simulates transient/prolonged resume busy periods; actual private-bus tests cover success without changing epochs and deadline failure/recovery. This finding changes implementation and testing, rather than changing elogind policy. [Pinned manager check](https://github.com/elogind/elogind/blob/v255.24/src/login/logind-dbus.c#L3532-L3538)

Finally, authenticated logical state is not itself proof that the restored app frame is on screen. The native replay now requires an ordinary KMS completion and capture before app input, and client-acknowledged down/up instead of an unobserved short tap. The earlier interrupted attempt remains separately recorded; partial runs cannot meet the twenty-consecutive-cycle gate. Stock restoration also distinguishes greetd/Phrog login from a separately PAM-authenticated Phosh desktop. [Procedure and limits](BUILDING.md#actual-rtc-woken-kernel-suspend)

The corrected native replay also extends the app fixture lifetime explicitly: the extended compositor harness alone had left `lock-probe` at its default 180 active seconds, stopping one attempt after sixteen validated cycles. With matching bounded lifetimes and presented/acknowledged app input, a fresh run passes twenty consecutive actual RTC/deep cycles, kernel success 35→55 and no failures, while preserving all partial attempts. [Recorded sample and limits](IMPLEMENTATION_STATUS.md#actual-kernel-suspend-and-rtc-wake)

## Native icon implementation follow-up (October 29)

The catalog already retains each desktop entry's Icon value. Feed native icon loading through an asynchronous, bounded raster cache while retaining original Tarot role art. Lookup must account for theme inheritance, nominal size and scale, with the mandatory hicolor fallback. [Freedesktop icon-theme specification](https://specifications.freedesktop.org/icon-theme/latest/).

At revision 34, a Rust SVG rasterizer was a candidate alongside the existing PNG decoder. The resvg API exposes tree-to-pixmap rendering and re-exports usvg/tiny-skia. usvg's default image resolver can read local file references, so Tarot must deliberately constrain references and decoded dimensions. That research required compiler/dependency/vendor checks, a device format inventory and rendering/theme decisions before implementation. The revision-35 decision below supersedes the earlier research-only state. [resvg API](https://docs.rs/resvg/latest/resvg/), [usvg image resolver](https://docs.rs/usvg/latest/usvg/struct.ImageHrefResolver.html).

Revision-35 decision: the phone inventory contains 40,686 SVG and 126 PNG paths across its installed icon collections, so PNG alone would leave much of that collection unresolved. Pin resvg/usvg 0.48.1 with only the text feature, keep PNG decoding explicit, use bundled Lato and override both image resolvers to reject imports. The inspected immutable manifest declares Rust 1.85; the full Tarot graph actually passes tests and ARM checking on the project's Rust 1.89 minimum. Cargo feature inspection confirms that system-font discovery and font memory mapping are disabled. The added 29 locked registry packages bring the vendor set to 446; introduced dependency notices ship in the APK. [Versioned renderer manifest](https://github.com/linebender/resvg/blob/v0.48.1/crates/resvg/Cargo.toml) · [Versioned resolver implementation](https://github.com/linebender/resvg/blob/v0.48.1/crates/usvg/src/parser/image.rs).

The native icon worker now resolves theme inheritance, nominal size/scale and hicolor, and produces bounded PNG/SVG rasters for Launcher, Quick Launch and lifted artwork. The packet's original role art retains priority. XPM, SVG image imports, live theme/catalog refresh and runtime scale changes remain explicit gaps. The resource guards do not establish hostile-document isolation or total process memory bounds.
