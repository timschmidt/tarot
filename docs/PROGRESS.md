## Revision history

Revision 66 reworks Sound page choices into **Play sound on** and **Record from** radio lists, with device modes as radio buttons too, so choosing a device never rearranges the page. It also fixes the headset's HFP mode showing as unavailable. The login screen's own services, including a PulseAudio that claimed the headset's hands-free link and microphone, kept running as the greeter user after login. An elogind drop-in now ends them when the greeter's session closes. On the phone, the owner switched outputs and A2DP/HFP from the Sound page after a reboot through Phrog, and next/previous were checked on a playlist. [Evidence](recordings/bluetooth-headset/README.md#sound-page-revision-66).

Revision 65 routes media keys to players. A Bluetooth headset's play and pause buttons, and any play/pause, next or previous key, control the player shown in the dashboard, also while locked, without waking the display. On the phone, the owner's JLab Studio paused and resumed GNOME Audio Player, unlocked and locked with the screen off, read back over MPRIS. The same headset also passes A2DP stereo and HFP wideband voice in both directions by ear, after re-pairing, because it had forgotten the phone's key. [Evidence and limits](recordings/bluetooth-headset/README.md).

Bluetooth pairing by touch passes (revision 64): with the phone near the host's test peer, Tarot discovers it, shows the numeric-comparison code (the peer received the same code), pairs, trusts, connects, disconnects and forgets, each step read back from BlueZ. Normal state was restored exactly, and an independent audit passed. The earlier `Page Timeout` was mostly distance. A separate, now unreproducible state in which Wi-Fi coexistence blocked incoming discovery and pages was cleared by reloading `brcmfmac`. Patch firmware, the 32 kHz clock, UART flow control and power saving were ruled out, and no platform change was needed. New host and phone tools check incoming reachability. Headset audio remains open. [Investigation and evidence](recordings/bluetooth-peer/README.md).

Bluetooth peer testing (on revision 64): with an owner-provided USB Bluetooth adapter on the host as a test peer, Tarot finds and selects it by touch. Pairing fails with `Page Timeout`, which BlueZ reproduces on the phone without Tarot, and the phone also doesn't answer inquiries, so this is a phone controller/firmware problem. Host and phone were restored exactly. [Investigation](recordings/bluetooth-peer/README.md).

Revision 64 follow-up: GNOME Audio Player (Decibels) appears in Tarot's media controls, and pausing it by touch corks its real audio stream. The test played generated silence through an owned null sink, so nothing was audible. [Evidence](recordings/media/README.md#a-real-player-gnome-audio-player).

Revision 64 adds media controls. Any app that exports the standard MPRIS interface appears in the notification dashboard with Previous, Play/Pause and Next. A host matrix covers discovery, text cleaning, stale and unsupported controls, signal floods, hung players and owner replacement. On the phone, Play and Pause work by touch. [Evidence](recordings/media/README.md).

Revision 63 makes direct boot safe to uninstall. greetd 0.10.3 refuses to start when its PAM service is missing, so the boot-destination helper now writes that service itself instead of the package shipping it. On the phone, Tarot was removed with direct boot still selected and the phone still booted to Phrog; reinstalling and choosing the login screen restored the original configuration exactly. [Evidence](recordings/boot-destination/README.md#package-removal-safety-revision-63).

Revision 62 adds the **At startup** choice: the login screen, or a direct, locked Tarot session through greetd's initial session. It was verified by reboot, by finger through Tarot's Polkit agent, and for keyring behavior. [Evidence](recordings/boot-destination/README.md).

Implementation is underway. ## Feature notes

On Linux with Rust, a C linker, libxkbcommon development files, and Wayland/EGL/GLES runtimes for the native keyboard:

```sh
cargo test --workspace
cargo run --bin tarot
cargo run --bin tarot -- -- gtk3-demo
```

F1 opens card overview; F2 opens the installed-app launcher. The bottom strip also provides overview access. Client arguments follow `--`. The launcher now discovers desktop entries, searches their metadata and launches them with structured arguments. GTK3, GTK4, Qt/Kalk and foot have rendered together on the phone; the [compatibility record](APPLICATION_COMPATIBILITY.md) distinguishes proven behavior from pending checks.

The interaction prototype now follows a strip drag into overview, browses cards horizontally and requests close with an upward card flick. Canceled drags settle back without opening the card; launcher scrolling stays within the launcher. Motion uses elapsed time, with `--reduced-motion` available. A real phone input replay covers these paths; faithful visual styling and the remaining shell features are still in development. See the [reference board](REFERENCE_BOARD.md).

In overview, hold a card to arrange it, drag onto another card to stack it, or use the separate-card rail to reorder/unstack it. Edge holds page through the deck. Each member remains its own native window; its menu also supplies move/stack/separate actions. These interactions have a [phone replay](BUILDING.md#native-stack-interaction-replay), including cancellation and closing one member while retaining its sibling.

A separate Rust/egui [native keyboard](BUILDING.md#native-egui-keyboard) now types into real GTK4 fields on the phone through the native text bridge. The same key view supports touch search in the launcher and masked Wi-Fi password entry. Letter and two symbol pages cover all 95 printable ASCII characters, with native touch replay coverage. Native typing uses Panfrost/GLES, reserves app space above the gesture strip and preserves app focus. The strip's Keyboard button reopens a hidden keyboard, and bounded process supervision recovers from a helper crash. These paths have real phone replay evidence; broader toolkit input, layouts and visual refinement remain in development.

An ordinary [egui application fixture](BUILDING.md#ordinary-egui-application-fixture) also runs as independent native cards, with phone tests for text/password entry, two windows, cooperative close and app-crash isolation. Its pinned egui host includes a direct-commit adapter. Multiwindow testing exposed and fixed hidden-window frame starvation; hidden clients now receive bounded callbacks while windows sharing a visible client remain responsive.

The development wrappers now enable a Rust [standard notification service](BUILDING.md#native-notifications) on their private session bus. Native notifications appear as bottom banners and remain in a touch dashboard. Revisions 43–44 add a [reserved notification well and source rail](NOTIFICATIONS.md), with exposed foreground interaction and a notification button/count in the gesture strip. Fifteen non-browser shell components now have passing current-package evidence across separate runs, with pages/restart and independent restoration audits. Browser compatibility and physical/visual acceptance remain open. Replacement, actions, expiry, do-not-disturb, preview hiding and input isolation have real phone replay evidence. Notification settings use a versioned TOML file with atomic saves. The service retries unavailable buses/names and retires old actions after a bus disconnect. History, authenticated lock privacy and notification styling remain in development.

The top-right status area now opens a [power and display menu](BUILDING.md#power-and-display-controls). With `--system-services`, battery/charging data comes from UPower and brightness changes go through the active local login session. Real phone taps changed brightness with driver readback, and the menu preserved native text focus on dismissal. Opt-in idle/panel paths and twenty consecutive actual RTC-woken kernel suspend cycles now have native evidence; broader wake/reliability coverage, power policy and a full Settings application remain in development.

The menu's [Audio page](BUILDING.md#audio-controls) now controls playback volume, mute and the default output for new playback through the existing sound server. Native phone taps passed independent server readback, temporary-output selection/removal, exact restoration and same-field typing. Microphone, headset/profile routing, call audio and acoustic validation remain in development.
