## Standard surface viewports and parent commits

Tarot now initializes/delegates Smithay's standard `wp_viewporter` implementation. Its double-buffered crop/destination state is validated by the existing buffer-commit handler and used by the renderer's surface view. No per-browser buffer-scale inheritance is introduced.

The new real-protocol regression uses independently colored SHM regions to check root and subsurface source crops, destination scaling, local input coordinates, source/destination commits without new buffers, viewport destruction and malformed-client isolation. It also changes a viewport while protected, requires diagnostic redaction and verifies the new pixels only after valid unlock. Duplicate viewport and out-of-bounds source requests disconnect only their offending clients.

That regression first exposes a separate pinned-Smithay defect: a desynchronized child remains at its old position after a parent-only commit. This matches upstream issue #1894. The local three-file adaptation of proposal #2141 at `e96548206bdb134c272ec302cb1e0f32fa580836` stages positions in parent transaction state, avoids stale child snapshots and applies all transaction state before callbacks. The proposal is unmerged; it is recorded separately from the existing damage backport and session-protection patch. [Issue](https://github.com/Smithay/smithay/issues/1894), [proposal](https://github.com/Smithay/smithay/pull/2141), [local attribution](../third-party/README.md).

The delayed-parent transaction test passes through Smithay's public server/client API, including a blocker and desync-to-sync transition, with a bounded deadline. Both scale-1/2 pixel/input replays pass. All 146 ordinary tests pass on current/minimum compilers, strict host/ARM checks pass, and existing lifecycle/transient, rounded cards, stacks, launcher, editor, terminal, helper-crash, lock/idle and rotation regressions pass. The three-file proposal patch independently applies to the published 0.7.0 source and matches the vendored files.

## Revision 35 activation investigation

The installed Firefox ESR is 140.12.0-r0, GTK3 is 3.24.52-r0 and mobile-config-firefox is 5.4.1-r0. GTK's matching source enables text input after a focused single non-drag touch release unless the on-screen keyboard is inhibited; enter and focus-in can also enable it. This is a candidate source of repeated activation, not proof of the original failure's cause. [GTK 3.24.52 input module](https://github.com/GNOME/gtk/blob/3.24.52/modules/input/imwayland.c). The Firefox inspection uses the moving ESR-140 branch, not an immutable source match to the installed package. [Inspected Firefox branch](https://github.com/mozilla-firefox/firefox/blob/esr140/widget/gtk/IMContextWrapper.cpp).

Text-input-v3 requires support for consecutive enable requests, and enable resets the previous text-input state. Identical surface IDs and content types do not establish that the focused field is unchanged. Suppressing resets solely on those attributes would weaken stale-input isolation. The currently published XML has interface version 2; the captured clients bind version 1, whose enable/reset contract already applies. [Protocol contract](https://raw.githubusercontent.com/wayland-mirror/wayland-protocols/main/unstable/text-input/text-input-unstable-v3.xml).

Three revision-35 follow-ups preserve the original touch timing, exact expected strings and 15-second gates. Each browser component passes 21 returns and its later checks. One combined run subsequently fails a card join because accumulated checkpoint serialization holds an edge contact across the 350-ms paging deadline. Deferring that checkpoint while contacts remain active makes the same combined replay pass all 13 components on the unchanged APK. This corrects measured recorder interference; it does not explain the retained revision-34 browser failure. [Timing comparison, source ledgers and limits](recordings/r35/README.md#subsequent-browser-and-recorder-investigation).

The inspected published Squeekboard source submits ordinary text from `handle_press`; release mainly completes its pressed-action bookkeeping. That differs from Tarot's release-based selection/cancellation. Adopting press-time submission would change interaction semantics rather than establish a safe association between a late activation and the preceding field tap. This is a source comparison, not a same-version installed Squeekboard trial. [Upstream submission source](https://world.pages.gitlab.gnome.org/Phosh/squeekboard/doc/src/rs/submission.rs.html).

Firefox's IME guide documents a process boundary between the native handler and focused editor, plus deferred editor notifications. This suggests that a surface-level round trip alone cannot prove DOM field readiness; it does not identify the callback responsible for the captured revision-36 activation. Keep the native browser gate and stale-context guard while advancing independent shell features. [Mozilla IME architecture](https://firefox-source-docs.mozilla.org/editor/IMEHandlingGuide.html).
